# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

Frijolero is a Ruby 4.0 web app. It runs Sinatra on Puma, in one process, with no database. It turns bank, card and brokerage statement PDFs into Beancount.

The flow: you upload a PDF. The app finds the account and the period, and you confirm. A background job extracts the transactions with OpenAI, applies YAML rules, writes a `.beancount` file, includes it in the ledger, and commits and pushes. The ledger is a git repo. The PDFs live in Backblaze B2. Version 2.0.0 replaced the CLI. The design record is `docs/webapp-plan.md`. The user docs, in Spanish, are `docs/setup.md`, `docs/ledger.md` and `docs/rules.md`.

## Commits

- Work happens on local `main`. The user pushes when they decide to. Do not open a PR for each change.

## Where things live

This repo:

```
config.ru        boots app/app.rb
app/             the Sinatra process: App and its route files, Dashboard, Jobs, views/
public/          style.css
lib/             the pipeline, no Sinatra: frijolero.rb is the manifest that requires the rest
templates/       prompts/ and ledger/, the seeds that bin/new-ledger copies; tests read prompts/classify
bin/             dev, test, test_fast, new-ledger
config/          deploy.yml, puma.rb
test/            mirrors app/ and lib/; fixtures/ holds sample statements and test prompts
```

The ledger repo is a private repo on GitHub. `CLAUDE.local.md`, git-ignored, holds its URL, the laptop path, the droplet, the host and the 1Password item. `bin/new-ledger` creates a ledger from `templates/`. The repo has three copies:

| Copy | Path | Who writes |
|---|---|---|
| Laptop | The clone on the laptop (SSH remote) | The user, with hand edits in fava. The fish function `moneys` pulls, runs fava, and commits and pushes on Ctrl-C. It pulls with rebase before each push. |
| Droplet volume | `/data/ledger` in the container (HTTPS remote, `GIT_TOKEN` header) | The app. Each job pulls with rebase first and commits and pushes last. The editors commit on save. `commit_and_push` pulls with rebase again between the commit and the push, because the laptop may have pushed in the meantime. A conflict aborts the rebase and raises, and the commit stays local. |
| GitHub | origin | Nobody directly. |

Layout of the ledger repo (`LEDGER_DIR`). `Config` derives each path from it:

```
transactions.beancount        # LEDGER_MAIN_FILE; inline txns + `include "accounts/AMEX/AMEX 2508.beancount"`
moneys.beancount              # what fava opens; includes transactions, account_opens, balances, prices
account_opens.beancount       # opens for every non-commodity account
config/accounts.yaml          # account key → beancount_account, openai_prompt_type, converter_type, description, closed, cutoff_day
config/rules/<Key>.yaml       # detailer rules, one file per account key (spaces kept: "BBVA TDC.yaml")
config/prompts/<type>/        # spec.json + instructions.txt + schema.json, read on every call
accounts/<Key>/<Key> YYMM.beancount   # + the .json next to it. Period = the month that holds most of the statement's days
```

On the volume, outside the repo: `/data/jobs.jsonl` is the append-only job log. `/data/incoming/<hex>/<original>.pdf` holds one directory per upload. The app removes that directory only when its job succeeds.

In B2, in a bucket shared with other apps: `frijolero/accounts/<Key>/<Key> YYMM.pdf`. `Config.pdf_key` is the only formula for that key, and `Config.pdf_prefix` is the account's directory.

A change to rules, accounts, prompts or model names is a commit in the ledger repo, not a deploy. The app reads those files on each request and each job. The volume gets the change at the next job's pull, with the "Actualizar" button on any report page, or from the shell with this command:

```bash
kamal app exec --reuse 'bundle exec ruby -Ilib -e "require %q(frijolero); Frijolero::LedgerRepo.new(dir: ENV.fetch(%q(LEDGER_DIR))).pull"'
```

## Environment variables

| Variable | Purpose |
|---|---|
| `LEDGER_DIR`, `LEDGER_MAIN_FILE` | The ledger clone, and the main file name (default `transactions.beancount`). `Config.data_dir` is the parent of `LEDGER_DIR`. |
| `OPENAI_API_KEY`, `OPENAI_POLL_TIMEOUT` | Extraction and classification. The poll timeout default is 900 s. |
| `APP_PASSWORD` | The only credential, checked by the login form; it also signs the 30-day session cookie, so changing it logs every device out. `/up` and static files are outside auth. |
| `B2_ENDPOINT`, `B2_BUCKET`, `B2_KEY_ID`, `B2_KEY` | S3-compatible B2. `B2.from_env` removes whitespace from the keys. A 1Password field once had a stray space. The symptom was `Signature validation failed`, or `400 IncompleteBody` for large bodies. |
| `GIT_TOKEN` | A GitHub fine-grained token with Contents read/write on the ledger repo. It travels as an HTTP header on each git call. It is never written to disk. |
| `PUMA_THREADS` | Thread pool size (3 in production). |
| `RLEDGER` | The rustledger binary for the reports (default `rledger` on PATH). The image ships 0.24.0 in `/usr/local/bin`. `brew install rustledger` on the laptop. |

## Architecture

### Request side (`app/`)

`App` holds the routes. `app.rb` has the settings, the collaborators, the dashboard and the jobs pages. `uploads.rb`, `statements.rb`, `editors.rb`, `accounts.rb` and `reports.rb` reopen the class for the upload flow, the statement page (with the PDF redirect), the rules editor, the Cuentas page and the reports. `app/` is the only place that requires Sinatra; `lib/` is the pipeline. The class has five class-level collaborators with `attr_writer`s, so tests can swap in fakes: `jobs`, `client` (OpenAI), `b2`, `repo` and `reports`. The app builds each one on first use.

`Login` in `app/login.rb` is a small Sinatra app used as middleware in `config.ru` before `App`. It owns `/login` (GET shows the form, POST checks the password), `/logout` (clears the session), and a `before` filter that redirects requests without a valid session to `/login`. `App` and its tests never see auth. The session cookie is signed, httponly, SameSite=Lax, Secure in production only, and lasts 30 days. The "Salir" button in the topbar posts to `/logout`. The login page is the cover of the manual: no topbar, the wordmark at column width over the heavy rule, a one-line tagline, and the field and the button on one row (`body.login`, `.wordmark`, `.tagline`, `.row` in `style.css`).

Views are standalone ERB pages in Spanish. There is no layout. Each page renders `app/views/_head.erb` through the `head` helper, which takes the title and an optional refresh, and `app/views/_topbar.erb` through the `topbar` helper, which is the wordmark plus Estados de cuenta and Reportes, with `aria-current` on the section that owns the request path (Reportes: `/reports` and `/journal`; Estados de cuenta: everything else). Every page of Estados de cuenta renders `app/views/_cuentas.erb` under the topbar: Recientes (the dashboard, `/`), Cuentas (`/accounts`) and Bitácora (`/jobs`), in that order, as a heading group like the reports title, with the current one as the `h1` and the rest as links, and the "Subir estado de cuenta" button at the right, which is the only way into `/upload` (the upload page itself hides it). A page that is none of the three keeps its own `h1` below the row. The pages of one account share `app/views/_account.erb`: the key as `h1` and a tab row, Estados (`/accounts/<Key>`, also current on a statement), Configuración (`/accounts/<Key>/config`) and Reglas (`/accounts/<Key>/rules`, only when the pipeline runs the detailer). Everything about an account lives under `/accounts/<Key>`; the statement is `/accounts/<Key>/<YYMM>`, and `Statements::PERIOD` constrains that segment to four digits so it never captures `config` or `rules`. The CSS is `public/style.css`, after the 1975 NASA Graphics Standards Manual: white ground, black type, one heavy rule under the header, thin rules elsewhere, NASA red only on the wordmark and on anything that needs action, NASA blue for links and the primary button. Public Sans everywhere, IBM Plex Mono for Beancount text, dates and amounts. One token set with `light-dark()` covers both color schemes. A status is a glyph plus a word (`.status.<name>`): received and ok ● in green (`--credit`), pending ○ in orange (`--debit`), queued ○ muted, running ◐, missing ▲ in red, failed ■ in red. Under 40rem every table hides its header row and each row becomes a block: the first cell is a `th scope="row"` heading, each `td[data-label]` becomes a label and value line, and an empty cell disappears, so a cell that may be empty must be written without whitespace inside. `Dashboard` computes received, missing, pending or failed for each active account, on each request. Its two columns are the newest period that some account has closed and the one before it. An account closes a statement on `cutoff_day` of each month (31, or unset, for the last day), and that statement belongs to the month 15 days before the closing date, the same rule as the classifier. An account whose cutoff has not arrived shows pending in that column. Corte shows `cutoff_day` from `accounts.yaml`. The job fills it in the first time a confirmed upload carries a printed period end, and never overwrites it, so a hand edit in `/accounts/<Key>/config` wins.

### Cuentas (`app/accounts.rb`)

`GET /accounts` lists the accounts from `accounts.yaml`, open ones first, closed ones last. Each has three links. `/accounts/<Key>` (the Estados tab) asks B2 for the PDFs under `Config.pdf_prefix` and shows period, upload date, size, a download link, and a link to the statement page when the `.beancount` exists. Every period between the oldest PDF and the newest one the account has closed (`Dashboard.last_closed`, from `cutoff_day`) gets a row; a period with no PDF shows `falta` with a link to `/upload`. A B2 failure renders the page with the error and status 502. `/accounts/<Key>/config` edits only that account's block of `accounts.yaml`. `AccountBlock` cuts the block by line range, from `Key:` to the next column-0 line, so the comments in the rest of the file survive. The save validates the block, splices it, validates the whole file, and commits `accounts <Key>`. The key of the block cannot change. `/accounts/new` is a form for one Default-pipeline account: key, description, Beancount account, prompt type from the `config/prompts` directories, optional cutoff day and opening date. `NewAccount` in `lib/` validates it, appends a block to the end of `accounts.yaml`, appends `<date> open <account>` to `account_opens.beancount` unless a line already opens that account, and commits `cuenta <Key>`. The other pipelines need extra accounts, so they go through `/accounts/yaml`, the whole-file editor.

### Upload flow

`POST /upload` saves the PDF under `incoming/` and runs `Classifier` in the request. If the file name parses as `<Key> YYMM.pdf`, the classifier answers without OpenAI. If not, it makes one OpenAI call with the `classify` prompt. It fills the account enum from `AccountConfig.descriptions`, makes sure that the dates are plausible, and derives `YYMM` from the midpoint of `period_start` and `period_end`, so the period is the month that holds most of the statement's days (AMEX Aug 4 to Sep 3 is `2608`). A doubtful result becomes `unknown`. The page then shows the result, and the person confirms. `POST /upload/confirm` validates the form and pushes a job. The second button, "Solo guardar PDF", posts to `POST /upload/backup`, which puts the PDF in B2 inside the request and removes the upload. It skips OpenAI, the ledger and the job log. It is for a statement whose `.beancount` already exists.

### Job

`Jobs` is one `Queue`, one worker `Thread` and `jobs.jsonl`. At boot it marks jobs left in `running` or `queued` as `failed`. There are no retries. The job body is: `repo.pull`, then `Statement#process`, then `repo.commit_and_push("<Key> YYMM")`, then remove the upload directory. The body runs with `Log.sink` pointed at the job output.

### `Statement`

`Statement` owns one PDF. The steps, in order: resolve account and period (arguments first, file name as fallback). Refuse if the outputs exist and `overwrite` is false. Upload to OpenAI, or reuse `file_id`. **Put the PDF in B2.** Extract. **Run `pipeline.validate!`.** Delete the local PDF. Save the JSON. Detail (Default pipeline only, and only if a rules file exists). Convert. Merge. Delete the OpenAI file.

The order protects the PDF. B2 has it before the paid step. The local copy survives each failure. Errors go through `OpenAIErrorReporter`, a policy table with one entry per `OpenAIClient::Error` subclass, and the result is `ERROR`. The job then fails with that status in its message.

### `Pipeline`

`Pipeline.for(account_config)` selects `Default`, `Multi`, `CetesDirecto`, `Fintual` or `Plata` from `converter_type`. A strategy gives the summary line, tells if the detailer runs (`runs_detailer?`), owns `validate!`, may shape the extraction request (`request_spec`), and calls its converter. Only `Default` and `Multi` have rules. `Multi` is a `Default` for one PDF that covers several accounts of the same bank, each in a "Movimientos de <name>" section: `accounts` in `accounts.yaml` maps the printed name to a Beancount account, `request_spec` puts those names in the `account` enum of the schema so the model never sees a Beancount name, `validate!` rejects a row whose `account` is not in the map, and `Converters::Default` posts each row from `sources[account]`. A transfer between two of those accounts appears once per section. A rule that points a row at another account of the same statement marks it as the one that stays, and `Multi#convert` drops its mirror, the row in that account with the same date and the opposite amount, from the JSON before converting. For the other pipelines the rules links, the rules editor and the detail button are gone, and `/accounts/<Key>/rules` is a 404. `validate!` raises `Pipeline::InvalidData` and names the missing table or field. Only `Default` rows have `date`, `description` and `amount`. For a pipeline that runs the detailer, the statement page reads the `.beancount` file, not the JSON: the JSON is frozen at job time, and the rules rerun, the edit dialog and fava change the file (`statement_rows` in `statements.rb`, over `Beancount::Parser` and `Beancount::Transaction`). The source posting is the one on `beancount_account`, or on one of a Multi's `accounts`, and gives the amount; the other postings are the classification, and `Expenses:FIXME` among them is unclassified. The page shows one entry per transaction: date, merchant (the `source_desc` when a rule replaced the narration, else the narration), the rest of the description muted, payee, the narration when it is a rule's, each account or a red `sin clasificar` with the Hacer regla button, a `!` flag, and the amount with thousands separators and a sign, green for credits and orange for debits (`money` and `split_description` in `app.rb`; the split is at the first `; ` or before an AMEX `RFC…` token, display only). The head is a `.page-head` like the journal's: the period between `‹ ›` links to the account's neighbouring statements (`statement_neighbours`), under it the count, the debit and credit sums per currency (`statement_totals`) and `● Todo clasificado` or `▲ N sin clasificar` (the FIXME count, from the file), and at the right "Descargar PDF" and "Aplicar reglas", which posts to `/detail` and appears only while something is unclassified, because the detailer touches only FIXME postings. The list and the Beancount text are two tabs made of two radio inputs and `:has()`, no script, styled as the journal's sort line. For the other pipelines the page shows only the extraction summary and the Beancount text. The Beancount text is colored by `beancount_html` in `statements.rb`, one regex over the escaped text: dates and comments muted, the flag bold and orange when it is `!`, accounts blue, `Expenses:FIXME` red, amounts green or orange by sign. Strings are matched only so that their contents stay plain. A line that matches nothing is plain text, so a hand edit never breaks the page. There is no highlighting library. A new statement type is one strategy plus one converter.

### Rules loop

`Detailer::Rules` is the pure matcher: `start_with`, `include`, an optional `when.amount`, and arrays with a fallback. `Detailer` applies it to the JSON. `BeancountDetailer` applies it again to an existing `.beancount` file. It touches only transactions that still post to `Expenses:FIXME`, so it is idempotent and hand edits are safe. Transactions with the `!` flag are invisible to it. `POST /accounts/:k/:yymm/detail` runs it and commits only if something changed.

The rules editor validates with `YAML.safe_load` and a probe call to `matches_for`. "Hacer regla" prefills a `start_with` entry with `YAML.dump`. That dump drops comments and reorders keys. This is accepted, but it is visible on a 600-line file. "Hacer regla" also sends the statement path as `back`. The editor shows it as a "Volver al estado de cuenta" link and keeps it in a hidden field, and the save redirects there with `?rules=1`, which the statement page turns into a notice asking to run the rules again. `back_path` honours only `/accounts/<Key>/<YYMM>`.

### Converters

`Converters::Default`, `CetesDirecto`, `Fintual` and `Plata` inherit from `Base` and share `AccountTargets` and `Amounts`. All amounts go through `BigDecimal`. A Float residue such as `-5.55e-17` breaks Beancount. `Amounts#money` and `Amounts#number` write thousands with commas (`-15,596.89 MXN`, `11,042 PORTMAN-E10F`). Beancount reads them, `bean-check` was run on a sample to confirm, and `Beancount::Transaction` strips them when it parses an amount back. `BeancountMerger` appends an `include` line relative to the directory of the main file.

### Plata reads Alpaca statements, never the advisor PDF

`Plata::Entry` flattens the four tables of the statement into one stream. The sort is stable on printed order, because reversals and the rows of one corporate action must stay adjacent. `Plata::CorporateAction` handles splits and spinoffs. They conserve cost basis. The removed total is authoritative, because Alpaca rounds the price on the added side. The sign of `quantity` separates removals from additions.

Three behaviours are deliberate. `High-Yield Cash Sweep` rows are skipped, because they double-count. `Journal Entry(Cash)` rows go to `Expenses:FIXME` for a hand edit, because their descriptions are UUIDs that no rule would match twice. A closing `balance` is asserted for cash and for each holding. A position exited mid-month is the one gap.

`Plata::Positions` opens commodity accounts with `"FIFO"` at the period start and closes them from `closing - moved`. Only commodity accounts are managed this way. Never declare them in `account_opens` too. A re-entry after a close in a later month collides at `bean-check`. The fix is to delete the earlier `close` and the later `open`. Commodity accounts must be `"FIFO"`. Beancount rejects `"AVERAGE"`, and `booking:` as indented metadata is ignored. The `plata` prompt copies `entry_type` verbatim, so an unknown type reaches the converter as a visible FIXME.

### Reportes (`app/reports.rb`, `lib/reports.rb`, `lib/period.rb`)

`/reports/income` and `/reports/balance` are whole-ledger reports. `Reports` runs `rledger query --no-cache -q -f json` (rustledger, a static binary; `Config.rledger`) on `moneys.beancount` (`Config.report_file`, the fava entry point, so options, opens, balances and prices are in), one BQL query per page (two for the balance sheet) plus `first_date`, and parses the JSON rows into `{account => {currency => BigDecimal}}`. Both row shapes are accepted: 0.22 prints objects, 0.24 arrays. `income(from, to)` sums Income and Expenses postings in the interval. `balance(at)` values every account on that day and adds three made-up equity rows, in the ledger's own signs, so that Assets − Liabilities = Equity holds on the page: `Equity:Utilidades-acumuladas` is Income plus Expenses up to that day, `Equity:Ganancias-no-realizadas` is cost over market of the assets (a second query, `COST(position)`, over Assets), and `Equity:Conversiones` is whatever is left, the effect of restating old cross-currency postings at the closing rate. `Reports::SYNTHETIC` lists the three; the table gives them no journal link. Both take `mxn:`, on by default: the total is `SUM(CONVERT(position, 'MXN', date))` at the closing date of the period (the income statement too, not per posting), which prices stocks through USD, and a commodity with no price stays in its own column. With `mxn: false` they are `SUM(position)` and `VALUE(SUM(position), at)`. `?mxn=0` on the page picks that, the "Por moneda" tab in the toolbar, and `report_query` carries it through every toolbar link and the period menu. `tree` adds the parent accounts with subtotals, in tree order, and leaves out accounts at zero. The views show one column per currency seen, income and liabilities with the sign flipped, and the two sections side by side from 60rem. Only the first level under each root is visible at load; a parent's name is a button and `public/reports.js` (one of the two scripts in the app, with `charts.js`) shows its direct children or hides and resets its subtree.

The span comes from `?period=`: `all`, `2026`, `2026-T3` or `2026-09`, parsed by `Period`; anything else means the current year. The income statement covers the period; the balance sheet is a snapshot at its last day, or today while it is still running. The title row is the two report names side by side, the current one as the `h1` and the other a light link at the same size, then the clone's last commit as "Datos actualizados al" (`LedgerRepo#head`, subject in the tooltip) and an "Actualizar" button that posts to `/ledger/pull`, runs `repo.pull` and returns to the report with `?pull=ok`, or with the git error in `pull`. The toolbar under it has the four resolutions (switching keeps the anchor date: from 2024 to Mes lands on December 2024), ‹ › around a menu of every period between `Reports.first_date` and today (the menu submits on change through `reports.js`), "al <today>" while the period is still running, and the currency tabs pushed to the right. That is the third way the droplet's clone catches up with the laptop, besides a job's first pull and the pull inside every commit. Measured on the real ledger: 0.07 s and 21 MB per query, so there is no cache. rustledger is stricter than Python beancount on one point: it warns when an account closes with a non-zero balance; `-q` keeps that off stderr and the query still runs.

**Diario** (`/journal`) is the third peer in the title nav. It lists the postings behind a report figure: every non-empty amount cell on both reports links to `/journal?account=<name>&period=…[&mxn=0]`, the Total row to the root, and the synthetic earnings row to nothing. `Reports.journal(prefix, from, to, mxn:, text:)` is one BQL query with the same date bounds and the same per-posting `CONVERT` as `income`, so the matched postings add up to the figure (movements only: a balance sheet figure is cumulative and is not reproduced). A parent account stands for its subtree and `''` means every account. The query has no account clause: it fetches every posting of the period with its transaction `id`, groups them into transactions in Ruby, and keeps the ones with a posting under the prefix, so each entry is a whole transaction with every posting and its amount. A posting under the prefix is `matched`, and matched postings come last. Each entry is a `details`: the summary is "Payee: narration" with the sum of the matched postings at the right in the report's sign, which is what adds up to the figure; open, it lists one line per posting in the ledger's own signs with the matched ones muted. Every segment of an account name, in the postings and in the heading, links to the journal of that prefix in the same period (`account_links`). No script: the fold is native. With no account every posting is unmatched, so there is no headline and no total. The date of an entry is the button that opens the edit dialog (see Editar); when `filename` matches `accounts/<Key>/<Key> YYMM.beancount` it also carries `data-statement=/accounts/<Key>/<YYMM>`, which the dialog shows as a link. `?q=` is one text filter on payee or narration; `Reports.bql_text` does `Regexp.escape` and turns `'` into `.`, because a BQL string cannot escape a quote. `?account=` is validated against `[A-Za-z0-9:-]` before it reaches the query and anything else is a 404. Under the toolbar, the account is the subtitle of the page (`h2.account`, mono, each segment a link, with a `<wbr>` after each colon so a long name wraps there on phones) in an `hgroup` with `p.net` under it, the count with thousands separators (`thousands`) and the total, smaller, and the search at the right. Phones center the heading group and stretch the search, with the chart menu on its own line under it. Under the head, or under the chart when there is one, `p.order` is the sort header: `?sort=` is `date-desc` (the default, newest first, same-day entries in ledger order), `date-asc`, `amount-desc` or `amount-asc` (`App::SORTS` in `app/sorting.rb`); "Fecha" and "Monto" each link to the flipped direction of their key, the active one in ink with ▾ or ▴ (`sort_link`), and Monto exists only with an account, because the amount is the headline sum of the matched postings in the report sign (`journal_sums` fills `tx[:sum]` once, for the view, the total and the sort; a sum in several currencies sorts by the first). An unknown value or an amount sort without an account falls back to the default, and only a non-default sort is written into the links. The page uses the report sign (Income, Liabilities and Equity flipped) and the `.ledger` list of the statement page. `report_query` carries `account`, `q` and `sort` only between journal pages (`filter:` is on only when the request path is `/journal`, and the title nav passes it off), so a filter never rides into a report and back into its amount links; it takes `mxn:` so the currency tabs keep the filter. No pagination: "Todo" on every account was 7,616 rows, 4.6 MB and 0.2 s on the real ledger. rustledger 0.22 prints rows as hashes and 0.24 as arrays in column order; `journal_row` reads both.

**Editar** (`app/edits.rb`, `lib/ledger_edit.rb`). The date of each journal entry is a blue text button (`button.edit`, with `data-file` and `data-line`) that opens a native `<dialog>` with the raw text of that one transaction, its file (a link to the statement page when there is one) and its lines. Every textarea resizes vertically only. The journal query also selects `filename` and `lineno`; `lineno` is the posting's line, and `LedgerEdit` walks back to the header (`YYYY-MM-DD` at column 0, any flag, so `!` transactions too) and takes the indented lines under it. `GET /edit?file=&line=` answers `{first, last, text}` and `POST /edit` saves. The save relocates the block and refuses with 409 when it no longer reads as the `original` the form carried (a job or a pull moved the file). It writes the edit, runs `Reports.check` (`rledger check --no-cache moneys.beancount`, 0.04 s on the real ledger, `--no-cache` so no cache file lands in the clone), and on any error puts the file back and answers 422 with one line per error, `E3001 <message> (<file>:<line>)`. The check is the whole ledger, so an amount change fails the next balance assertion in `balances.beancount` by design, and one pre-existing error anywhere blocks every edit. A clean check commits and pushes through `commit_and_push` with `Edición <Key> <YYMM>: <date> <payee or narration>` as the subject and the block before and after as the body; a git failure is 502 and the file stays saved and committed locally. A failed check is 422 with the errors as JSON, `{errors: [{code, message, file, line}]}` (`Reports.check` returns those hashes; `LedgerEdit::Invalid` carries them and joins them into its message). The dialog's form is the same `form.code` as the statement's editor (see Editor de archivos), opened by `editor.js` with the block's text and its first line, so the gutter shows the file's own line numbers and an error's line maps to the same `#L<n>`; 204 reloads in place, which keeps the scroll position. `file` and `line` are checked by `LedgerEdit` itself: a path outside `LEDGER_DIR` or not ending in `.beancount` is 404. There is no lock against the job worker, same as the rules editor.

**Editor de archivos** (`app/views/_code.erb`, `public/editor.js`). The Beancount text of a statement, and any `.beancount` file of the ledger at `/files/<path>`, is a `form.code`: a `pre` with one `span.line#L<n>` per line (`beancount_html` splits on `"\n"` and keeps the trailing empty segment; `beancount_line` colors one line), the number as a CSS counter in the pre's left padding, a hidden textarea and hidden actions. Without JS it reads as before. "Editar" (`button.edit-file`, at the right of the tab row on a Default statement, next to the `Beancount` heading elsewhere, next to the path on `/files`) fetches `GET /edit?file=` without a line, which is the whole file, and lays the textarea over the pre: transparent text, the ink caret, the same font, padding and wrapping (`white-space: pre-wrap; overflow-wrap: anywhere`), so the pre keeps the colors and sets the height and there is no scroll to sync. On every keystroke the pre is redrawn with the JS copy of `BEANCOUNT_TOKEN` in `editor.js`; the two regexes must stay identical. Nothing inside `.surface` may change a line's height, or the caret drifts, which is why an error's message is a `title` and a list entry, never inline text. Tab inserts two spaces and ⌘S saves. The save is `POST /edit` with the whole file as `original` and `content`; `LedgerEdit` with `line` nil or 0 is the whole file, and its commit subject is `Edición <Key YYMM or path>` with no body. 204 reloads with `?saved=1`, which shows `Guardado` and, on a statement, opens the Beancount tab. 422 lists the errors under the editor: one of this file marks its line (`.line.err`, red number and a light red band) and links to `#L<n>`, which also puts the caret there; one of another file links to `/files/<file>#L<n>`, where `:target` marks the line. 409 and 502 are text in the same list. Cancelar redraws the original and leaves edit mode without a reload; in the dialog it also closes it. `editor(form)` in `editor.js` wires one form and returns `open(text, first)` and `showErrors`; the page wiring under it is the Editar button and the journal's date buttons. `/files/*` is `LedgerEdit`'s path check: outside the ledger or not `.beancount` is 404; a statement file shows a link to its page. In read mode the trailing empty line is hidden (`.code:not(.editing) .line:last-child:empty`); in edit mode it shows, as in any editor.

**Gráficas** (`app/charts.rb`, `public/charts.js`, `public/d3.min.js`). A report can have a chart block. It exists only when the person asks for it: a menu sets `?chart=<name>`, `report_query` carries it with the journal filter, and a page without it renders no block, no data and no script. Today only the journal of one account has charts. Its menu is a `<select name="chart">` inside the search form of the journal head, so choosing a chart submits the search text with it (`reports.js` submits it on change, like the period menu); "Gráficas…" is the empty first option and closes the chart. The charts are `App::CHARTS`: `history` (Histograma), `accounts` (Subcuentas) and `payees` (Contrapartes). `chart_options` decides which are offered: a treemap needs at least two groups, and one that has fewer is a `disabled` option; a request for a disabled chart counts as none (`chart_name`). The block comes right under the head row, above the movements. Ruby embeds the rows the page already has as JSON in `<script type="application/json" id="chart-data">` (`chart_data`: the chart name, the period as drawn, a running one cut at today, and the matched postings as date, currency, amount in the report sign, account and payee, so the bars and the tiles add up to the total on the page) and `charts.js` aggregates and draws with d3. A new chart on the same rows is JS only; one that needs other data gets its own query in `Reports`, run only when that chart is on. The library is d3 7.9.0, vendored as the UMD `dist/d3.min.js` in `public/` (no node, no bundler, no CDN; the ESM entry on the CDN is a graph of 30 module URLs, so there is no single ESM file) and loaded with classic deferred `<script>` tags before `charts.js`, so `d3` is a global. Upgrading is replacing the file. The histogram offers the buckets finer than the page's resolution (Mes → día; Trimestre → día, mes; Año → día, mes, trimestre; Todo → all four; defaults día, mes, mes, año), as buttons inside the block, client-side and not in the URL; gaps are zero; one figure per currency, with a caption only when there is more than one. Over month, quarter or year buckets the x axis labels every nth bar with the bucket's own label; over day buckets it marks the starts of months, quarters or years, the finest that gives at least two marks and at most one per 80 px, with January written as the year, like d3's own time axis, and a single month falls back to every nth day. The amount axis writes the full number under a thousand and K or M above it (`short`). A bar over a month, quarter or year is an SVG `<a>` to the same journal with that period (`link` keeps the rest of the query, so the chart stays open), blue on hover; a day bar is not a link. The treemaps group the matched amount by the first segment under the account, or by payee, one figure per currency: a group at or below zero has no area and is left out, groups under 1 % of the total merge into "Otras", and a tile shows its name and amount when they fit (about 7.5 px per character, 14 px per line). A subaccount tile links to that account's journal, a payee tile to the same journal with the payee as `q`; "Otras", "Sin subcuenta" (postings on the account itself) and "Sin contraparte" link nowhere. Tiles are ink at four tints by the square root of the share of the largest tile (100, 70, 25 and 10 percent, `tint`), with page-colour gutters, so magnitude reads by tone as well as area and dark mode inverts through the token; labels reverse out on the two dark steps (`.on-ink`) and no tile lands on a midtone. A linked tile turns blue on hover with its label in `--on-blue`. A tooltip (`.tip`, one `div` per block, positioned with `d3.pointer`) shows the bucket or the group and the amount. In MXN mode a bar of a long period and the page it links to can differ by a few pesos on accounts with foreign-currency postings, because `CONVERT` prices at each period's own closing date. Dates are plain days: `d3.utcParse` and the `utc` intervals keep them as written. Charts are SVG with a `viewBox` at the block's width and a height of 200, so they scale on phones, and they take every color and font from `style.css` (`.chart .bar`, `.bar.debit`, `.tile`, `.label`, `.tick`, `.zero`, `.tip`), never from attributes set in JS, so dark mode and the NASA palette hold. Rack tests cover the menu, its options and the JSON; the drawing is checked by eye in Safari against the page total. There is no JS test runner by design.

### Infrastructure classes

`OpenAIClient` has a nested `Transport` and typed errors. `extract_transactions(file_id, spec)` runs any prompt spec on a file, with `background: true` and a 2 s poll. The classifier uses it too. `B2` is a hand-rolled SigV4 client over `Net::HTTP`, with path-style URLs. `list(prefix)` reads one page of ListObjectsV2 and parses the XML with a regex. `uri_encode` is the only place that turns a space into `%20`. The tests replay two official AWS vectors. `LedgerRepo` runs git as a subprocess (see "Git subprocesses"). `Log` writes plain lines to `Log.sink`. `PromptSpec` assembles `spec.json`, `instructions.txt` and `schema.json`. The templates live in `templates/prompts/{default,multi,plata,classify}`. The ledger repo holds the live copies, and `bbva`, `cetes` and `fintual` exist only there.

## Git subprocesses

`GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` override `chdir:`. If they are set, a test that runs git "in a tmpdir" commits to this repo instead. It happened once. Each git subprocess, in lib and in tests, gets an env hash that sets every `ENV` key that matches `/\AGIT_/` to nil. `LedgerRepo#git` does this, and `test/ledger_repo_test.rb` has the regression test. Before you commit new code that touches git, run `GIT_DIR=$(pwd)/.git GIT_WORK_TREE=$(pwd) bundle exec rake test` once and make sure that `git log -1` did not move.

## Operations

- **Deploy.** Kamal 2 with `config/deploy.yml`, which holds the droplet, the host, the image and the bucket. The image is built for amd64 on the laptop. The volume is `frijolero_data:/data`. The memory cap is 128 MiB.
- **Secrets.** `.kamal/secrets` fetches each secret from a 1Password item with `kamal secrets fetch --adapter 1password`. Write one command per line, because the Kamal parser has no line continuations. The fields are `kamal_registry_password`, `openai_api_key`, `app_password`, `b2_key_id`, `b2_application_key` and `git_token`. The non-secret `b2_bucket` and `b2_endpoint` are copied into `deploy.yml`.
- **From the shell of Claude,** `kamal` and `ssh` to the droplet work only while the 1Password app is unlocked. The `op` prompt and the SSH agent both go through it. If they fail with `promptError` or "communication with agent failed", ask the user to run the command with the `!` prefix. A failed deploy can leave a lock. `kamal lock release` removes it.
- **Measured.** Idle production memory is 35 to 42 MiB of cgroup memory, or 46 to 52 MB of RSS. A report adds a ~21 MB `rledger` child for ~0.1 s. The cap is 128 MiB. A deploy takes about 40 s.
- **Dockerfile.** `ruby:4.0.6-slim`, two stages, user `app`, with `git` installed for `LedgerRepo` and the `rledger` binary (downloaded with a pinned checksum in the build stage) for the reports. `Gemfile.lock` pins Bundler to 4.0.16, the version in the image.
- **Failed job.** The job page shows the captured output. The PDF stays in `/data/incoming/<hex>/`. There is no retry from disk. The person uploads again. Stale directories accumulate, and nothing removes them yet.

## Tests

Minitest and rack-test, about 520 tests, about 5 s. `test/` mirrors `app/` and `lib/`. `with_ledger_dir` points `LEDGER_DIR` at a temporary directory with `config/`. Web tests call `App` directly and swap the collaborators for fakes. Only `test/app/app_test.rb` loads `config.ru`, for the auth wiring. `test_helper.rb` sets `RACK_ENV=test` before it loads the app; Sinatra fixes its environment when `sinatra/base` loads, and any other value makes host authorization return 403 in tests. No test touches the network. `Config.accounts` is read on each call and never memoized. The first deploy cached `{}` because it booted before the volume had a ledger.

## Known rough edges

1. `POST /upload` blocks on the classifier: background mode plus a 2 s first poll. Two options: a synchronous Responses call with `reasoning.effort: minimal`, or a classify job with a page that refreshes. The model is `gpt-5.4-mini`, set in `config/prompts/classify/spec.json` of the ledger.
2. One worker thread. A second upload waits behind an extraction.
3. "Hacer regla" rewrites the whole rules file and drops comments.
4. A `closed: true` account leaves the dashboard. Its history lives on its page, reached from Cuentas.

## Data formats

Transaction JSON for the Default pipeline. The other pipelines have their own schemas in `config/prompts/<type>/schema.json`:
```json
{ "transactions": [ { "date": "2024-01-15", "description": "AMAZON WEB SERVICES", "amount": -50.00,
                      "currency": "MXN", "payee": "optional", "narration": "optional", "expense_account": "optional" } ] }
```

Rules YAML:
```yaml
start_with:                 # description starts with PATTERN
  PATTERN: { payee: "Name", narration: "Text", account: "Expenses:Category" }
  PATTERN2:                 # with a condition: exact amount
    when: { amount: -149 }
    payee: "Name"
    account: "Expenses:Category"
  PATTERN3:                 # list: first matching `when` wins; the entry without `when` is the fallback
    - { when: { amount: -15000 }, payee: "Landlord", account: "Expenses:Rent" }
    - { payee: "Transfer", account: "Expenses:Misc" }
include:                    # description contains PATTERN; same entry shapes
  PATTERN: { account: "Expenses:Food" }
```
